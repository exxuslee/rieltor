# План локального хранения сообщений и объявлений

Дата: 2026-09-15. Статус: проект плана; реализация не начата.

## 1. Цель и согласованные решения

Единый источник объявлений — локальная SQLite через существующий Room. Лендинг и репосты читают подготовленные объявления из одной базы.

- Строго две прикладные таблицы: `incoming_telegram_messages` и `listings`. Все прежние служебные таблицы заменяются полями этих сущностей или файлом `settings.json` в корне проекта. Внутренние метаданные SQLite/Room не являются прикладными таблицами.
- После редактирования сохраняем новую версию и ждём ещё 20 минут без изменений. Подтверждено пользователем.
- Служебные параметры ключ–значение и глобальное состояние лимитера хранятся в `settings.json`. Статусы и история конкретного репоста принадлежат объявлению и хранятся в listings.
- «Перевести во вторую таблицу» означает транзакционно создать/обновить объявление и отметить входящую запись обработанной. Исходную запись сохраняем для проверки и восстановления.
- Очереди постоянные, выбирают самые свежие доступные записи; старые не удаляются при достижении 64 сообщений.
- План касается backend и подключения каталога. Текущий репозиторий расположен в `D:\git\rieltorSite`, frontend — в `docs`. Указанный в AGENTS.md путь исходников сайта `D:\Android\rieltorSite` отсутствует. Перед реализацией frontend нужно согласовать актуальный путь; этот план не переносит файлы сайта.

## 2. Что обнаружено в текущем коде

- Room версии 11 содержит `received_telegram_messages`, `telegram_repost_queue`, `published_reposts`, `repost_publications` и служебные таблицы TikTok.
- `TelegramClientAdapter` удерживает сообщение 20 минут в памяти; затем запрашивает актуальную версию. При недоступности проверки может продолжать с ранее полученным содержимым. Перезапуск теряет незавершённое ожидание приложения.
- `TelegramMessageMapper` вычисляет `updateId` из chatId и ID сообщения/альбома. Это не настоящий messageId; обратное восстановление для альбомов неоднозначно.
- `TelegramRepostCoordinator` берёт старейшую запись FIFO, затем ждёт мастер-лимитер. Очередь ограничена 64 ожидающими сообщениями с вытеснением старых.
- `PublishPhotoRepostUseCase` скачивает Google Drive непосредственно перед репостом и сохраняет публичные фото. Загрузка зависит от доступности публикации.
- `RepostMasterLimiter` управляет слотами, но сам не выбирает объявления.
- `MediaCleanupJob` удаляет фото старше 4 дней; `TelegramHistoryCleanupJob` чистит историю старше 30 дней. Эти правила нельзя применять к активному каталогу.
- Каталог сейчас использует `docs/js/data.js`; статические страницы генерируются `docs/scripts/generate-seo-pages.mjs`.

## 3. Таблица входящих сообщений — incoming_telegram_messages

Одна строка на настоящее Telegram-сообщение. Для альбома несколько строк объединяются по `(chatId, mediaAlbumId)`.

| Поле | Тип / назначение |
| --- | --- |
| id | Локальный первичный ключ |
| chatId, messageId | Int64, уникальная пара; настоящий Telegram ID |
| messageThreadId | Int64, исходная тема; 0 при отсутствии темы |
| mediaAlbumId | Int64 nullable, связь частей альбома |
| originalRawMessage | Неизменяемый первый снимок сообщения |
| rawMessage | Актуальный сериализованный снимок: текст/подпись, entities со скрытыми ссылками, ID и метаданные медиа |
| rawText | Актуальный исходный текст для парсера |
| sourceCreatedAt, sourceEditedAt | Время сообщения и правки в Telegram; edited nullable |
| receivedAt, updatedAt | Время первого локального получения и последнего изменения строки |
| contentHash, revision | Отпечаток значимого содержимого и монотонная версия |
| stableSince, verifyAfter, verifiedAt | Начало стабильности, срок проверки и время успешной проверки |
| status | Состояние обработки, перечислено ниже |
| googleDriveUrls | JSON-массив найденных ссылок, включая ссылки из entities |
| mediaManifest | JSON: выбранные Drive fileId/version, порядок, локальные относительные пути, размеры, hash, результат скачивания |
| attemptCount, nextAttemptAt, lastError | Повторы этапа, следующая попытка, диагностическая причина |
| leaseToken, leaseUntil | Временное владение работой; защищает от двойного выполнения и зависания после сбоя |
| listingId, promotedAt | Ссылка на готовое объявление и время переноса |
| deletedAt | Подтверждённое удаление источника, nullable |
| legacyUpdateId, legacySnapshot | Nullable: старый вычисляемый ключ и сохранённые данные миграции |

Состояния: `WAITING_STABILITY → READY_FOR_MEDIA → DOWNLOADING → MEDIA_READY → PROMOTED`.
Дополнительные: `VERIFY_RETRY`, `MEDIA_RETRY`, `NEEDS_REVIEW`, `DELETED`. При новой версии — возврат в `WAITING_STABILITY`.

Индексы: UNIQUE `(chatId, messageId)`; `(status, verifyAfter)`; `(status, nextAttemptAt, sourceCreatedAt DESC, id DESC)`; `(chatId, mediaAlbumId)`; `listingId`.

Исключение для миграции: messageId может быть null только у legacy-записи NEEDS_REVIEW с legacyUpdateId; новые сообщения всегда имеют настоящий ID. Использовать частичный уникальный индекс для ненулевых ID и отдельный уникальный legacyUpdateId. Неизвестный ID нельзя синтезировать.

Raw остаётся внутренним: не отдавать на сайт чужие контакты, служебные заметки или закрытые Drive-ссылки.

| sourceRevision | Версия/отпечаток подготовленного источника, защищает от устаревшей записи |
| title | Очищенный заголовок на украинском |
| description | Очищенное публичное описание |
| location | Нормализованный код: IRPIN, BUCHA, VORZEL, HOSTOMEL; для прочих мест OTHER |

| googleDriveUrl | Основная исходная ссылка, nullable только для проверяемых legacy-записей |
| googleDriveUrls | Полный массив исходных ссылок, чтобы не потерять текущую поддержку нескольких папок |
| price | Int64 в минимальных единицах валюты, без Float/Double |
| currency | Код валюты: USD / UAH / EUR |

| areaM2, landAreaSotka, rooms, floor, totalFloors | Типизированные характеристики для карточек, сортировки и будущих фильтров; nullable, если не указаны |
| photos | JSON-массив: mediaId, относительный путь, порядок, width, height, alt, sourceFileId, sourceVersion, checksum |
| coverPhotoId | Обложка из photos |
| status | ACTIVE / NEEDS_REVIEW / HIDDEN / SOLD / ARCHIVED |
| sourceCreatedAt, receivedAt | Исходная свежесть и время получения, не меняются при повторной обработке |
| cdt, updatedAt | Создание строки объявления и последнее обновление |
| publishedAt | Первое появление на сайте, nullable |
| tiktokReposted, threadsReposted | Boolean NOT NULL DEFAULT false; true только после подтверждённой публичной публикации |
| tiktokRepostedAt, threadsRepostedAt | Время подтверждённого репоста, nullable |
| tiktokStatus, threadsStatus | Индексируемые текущие состояния направлений |
| tiktokPublishId, threadsPublishId | ID последнего внешнего задания, nullable |
| tiktokState, threadsState | JSON: mode, attemptId, attemptCount, leaseToken/leaseUntil, nextAttemptAt, createdAt, updatedAt, lastCheckedAt, lastError и история попыток с их publishId/статусами |
| legacyUpdateId, legacySnapshot | Старый ключ и исходные данные миграции, nullable |
| parserVersion, parseWarnings | Версия извлечения и причины неполных/неоднозначных данных |

Исправления названий: `raw-message → rawMessage`, `govermentPrograms → governmentPrograms`.

Для legacy-объявлений NEEDS_REVIEW разрешить неизвестные messageId и неполные обязательные публичные поля; ограничения ACTIVE требуют настоящую идентификацию и валидное содержимое. Уникальность источника задаётся частичными индексами для известных ID. Старые публикации без полного raw сохраняются здесь с legacySnapshot, без создания вымышленного объявления для сайта. Статусы/ID в отдельных колонках — источник текущего состояния; JSON хранит дополнительные сведения и прошлые попытки. Обновлять их и Boolean одной транзакцией. Все незавершённые publishId сохранять независимо от числа прошлых попыток.

`TELEGRAM_MONITORED_MESSAGE_THREAD_IDS` — список отслеживаемых тем, а не тип недвижимости. Добавить явное соответствие `(chatId, messageThreadId) → typeOfRealty` в конфигурации. Реальные ID взять из конфигурации и согласованного соответствия, не угадывать. Неизвестный тип — `NEEDS_REVIEW`.

Параметры хранят факты, отсутствующее значение — null. Типизированные столбцы являются источником для одноимённых характеристик в API; не поддерживать независимо две редактируемые копии в JSON. Программы извлекаются из текста с учётом отрицаний; «єОселя» нельзя приписывать по типу объекта. Уточнение конкретной постановы хранить в дополнительных параметрах, если оно есть в источнике.

Индексы: уникальные ключи источника; `(status, sourceCreatedAt DESC, id DESC)`; `(status, location, typeOfRealty, currency, pricePeriod, transactionType, price)`; при необходимости отдельные ценовые/локационные индексы по результатам EXPLAIN. Для четырёх программ использовать JSON membership, предварительно проверить поддержку в bundled SQLite; при росте каталога — индексируемая производная маска, а не поиск подстрокой.

## 5. Получение и проверка Telegram

1. Сразу сохранять входящее сообщение, до ожидания и скачивания. Повтор того же события не сбрасывает таймер и не создаёт дубль.
2. Вычислять `verifyAfter = stableSince + 20 минут`. При изменении значимого содержимого/версии правки обновлять snapshot, повышать revision, начинать ожидание заново.
3. Добавить обработку событий удаления. Отличать окончательное удаление от очистки локального кэша и от недоступности сообщения/чата.
4. Постоянный проверяющий worker выбирает записи с наступившим verifyAfter и повторно запрашивает источник. Ошибка сети/доступа означает VERIFY_RETRY, а не разрешение скачивать или доказанное удаление.
5. Если версия совпала — READY_FOR_MEDIA. Если изменилась — сохранить новую и ждать. При подтверждённом удалении — DELETED.
6. Альбом проверять целиком. Новая часть/правка меняет общую версию группы и срок стабильности; один альбом создаёт одно объявление. Подтверждённое удаление части требует повторной проверки всей группы, без публикации прежнего состава.
7. После перезапуска продолжать сроки из БД, повторно проверять готовые записи перед работой. При восстановлении TDLib сверять незавершённые группы; поведение доставки пропущенных событий проверить интеграционно.
8. Для уже подготовленного объявления правка источника скрывает старую версию до повторной подготовки; удаление переводит её в HIDDEN и запрещает новые репосты. История завершённых репостов сохраняется; внешние опубликованные посты автоматически не удаляются.

## 6. Независимый GoogleDriveDownloadWorker

Одна постоянная логическая очередь — выборка из incoming, один worker, одновременно одно сообщение/альбом и один файл. Сервис запускается вместе с приложением и не зависит от включённости TikTok/Threads.

1. Выбирать READY_FOR_MEDIA или MEDIA_RETRY с наступившим nextAttemptAt, без действующей lease: `ORDER BY sourceCreatedAt DESC, id DESC LIMIT 1`. Для альбома свежесть определяется закреплённым головным сообщением.
2. Атомарно захватить группу с leaseToken и ожидаемой revision. Уже начатую загрузку не прерывать просто из-за нового сообщения.
3. Перед скачиванием повторно подтвердить стабильность источника: ожидание очереди могло быть долгим.
4. Разобрать поля объявления. Отсутствие цены, ссылки, неизвестный тип/валюта/локация без надёжного разбора — NEEDS_REVIEW с причиной, без выдуманных значений и потери raw.
5. Получить manifest поддерживаемых изображений из всех ссылок с учётом пагинации, убрать дубли по Drive fileId, зафиксировать порядок и версию. Скачать последовательно во временную папку конкретной revision; не удерживать весь альбом в памяти.
6. Проверить формат и целостность, применить EXIF, подготовить JPEG и размеры для сайта. Сохранить проверенные файлы атомарным переименованием. Каталожный лимит фото задаётся отдельно от платформенных лимитов репоста.
7. Считать загрузку завершённой только после успешной подготовки всех выбранных изображений manifest и минимум одного фото. Ошибка части пакета не выдаёт неполное объявление за готовое; уже проверенные неизменившиеся файлы использовать при повторе.
8. Сохранить MEDIA_READY. Повторно сверить Telegram revision и завершить PromoteListingUseCase: транзакция upsert listings + PROMOTED для всей группы. Проверка revision/lease внутри транзакции обязательна; сетевые запросы и файлы вне транзакции.
9. Если источник изменился/удалён во время загрузки, не активировать устаревшую версию. Неиспользованные файлы позже удалит уборщик. Сбой после переименования файлов, но до commit, восстанавливается по manifest без дублей.
10. После завершения брать следующее самое свежее доступное сообщение. Между файлами/заданиями — настраиваемая небольшая пауза; при пустой очереди ждать сигнал с периодической проверкой БД.

Повторы: экспоненциальная задержка с jitter, уважение Retry-After, конечное число попыток с переводом в NEEDS_REVIEW. Проблема доступа/OAuth отражается отдельной диагностикой; ошибка одного объявления не блокирует остальные. При заполнении диска приостановить загрузки без удаления активных фото и входящих сообщений.

Строгий приоритет свежих означает, что при постоянном избытке новых сообщений старые могут ждать долго. Это соответствует запросу; показывать размер и возраст хвоста очереди, не вводить скрытую смену порядка.

## 7. RepostService и RepostMasterLimiter

- Очередь репостов — постоянная выборка готовых ACTIVE-объявлений из listings с доступной локальной галереей и незавершёнными включёнными направлениями. Отдельная копия raw/фото в telegram_repost_queue больше не нужна.
- Сначала определить наличие работы и дождаться разрешения мастера; после ожидания выбирать самое свежее доступное объявление заново. Не закреплять прежнюю голову на весь cooldown.
- Рефакторинг API лимитера: после ожидания захватить свежего кандидата в SQLite, затем надёжно сохранить резерв слота в settings.json до внешней отправки. Общей транзакции SQLite и файла нет; протокол восстановления описан в разделе 9. Пустая очередь не расходует квоту.
- RepostMasterLimiter отвечает за интервал, суточную квоту и сохраняемые глобальные паузы. Выбор и lease объявления принадлежат координатору. Лимитер не запускает Google Drive.
- PublishPhotoRepostUseCase получает готовые локальные фото и структурированные поля; больше не скачивает и не парсит источник. Ограничения количества фото каждого назначения применяются при подготовке его запроса.
- TikTok и Threads исполняются раздельно, последовательно для одного объявления, с независимыми исходами. Успех одного не откатывается ошибкой другого.
- Одних Boolean недостаточно для очереди: `false` бывает у нового, отключённого, ожидающего подтверждения и ошибочного репоста. Используем tiktokStatus/threadsStatus и tiktokState/threadsState внутри listings, без repost_publications. Захват направления — условное обновление строки по статусу и lease; добавить индексы `(status, tiktokStatus, sourceCreatedAt DESC, id DESC)` и аналогичный для Threads.
- Статусы назначения: PENDING, PROCESSING, AWAITING_CONFIRMATION, DELIVERED_DRAFT, PUBLISHED, FAILED, UNKNOWN, SKIPPED_DUPLICATE. Отключённые направления не участвуют в выборке.
- Сохраняем прежнее правило ошибок: FAILED не повторяется автоматически только потому, что Boolean false. Повтор — явный возврат в PENDING. Временный запрет лимитера оставляет задание ожидающим до снятия паузы.
- `tiktokReposted/threadsReposted = true` и время репоста записываются в одной транзакции с подтверждённым PUBLISHED. Для TikTok DRAFT доставка в inbox означает DELIVERED_DRAFT и false; повторно загружать такой draft нельзя. Подтверждение публичного поста позднее меняет Boolean.
- Перед повторной отправкой после сбоя проверять сохранённый publishId. Если внешний запрос мог выполниться, но ответ потерян, использовать UNKNOWN и сверку; не отправлять вслепую. Абсолютная exactly-once гарантия без поддержки внешнего API невозможна.
- Сохранить текущую проверку pending shares, интервалы и квоты. Пауза TikTok не приостанавливает получение Telegram, загрузку Drive и каталог.
- Повторные Telegram-события отсекаются уникальными ID. Старое эвристическое совпадение цены/адреса/темы использовать осторожно для репостов, с учётом chatId; оно не должно автоматически удалять разные объекты из каталога. SKIPPED_DUPLICATE исключается из очереди, но не выдаётся за собственный подтверждённый репост.
- Повторная подготовка объявления не сбрасывает ранее подтверждённые Boolean и историю. Автоматический репост новой редакции уже опубликованного объекта в этот этап не входит.

## 8. Каталог и фильтры лендинга

Добавить `GET /api/listings` и `GET /api/listings/{id}`. Лендинг читает JSON из backend, локальная SQLite доступна только backend.

Параметры списка:

Автоконвертация валют в этот этап не входит.

По умолчанию показывать все ACTIVE-объявления постранично, новые первыми, независимо от репостов. Сортировка имеет стабильный второй ключ id, cursor учитывает фильтры и сортировку. Установить верхний предел limit. Неизвестные коды/некорректный cursor — 400. Закрытое объявление по ID не раскрывает внутренние данные.

## 9. Хранение фотографий и служебных данных

- Фотографии активных объявлений не имеют TTL в 4 дня. Уборщик удаляет только неподключённые временные файлы и медиа без ссылок от объявлений/незавершённых внешних публикаций, после защитного периода.
- Сохранять стабильные относительные пути и mediaId, формировать публичные URL от настроенного base URL. OAuth-ссылки не являются ссылками галереи.
- Очистка истории не удаляет незавершённые сообщения, ссылки каталога, неподтверждённые публикации и сведения, необходимые для защиты от дублей. Срок хранения завершённых raw согласовать отдельно; первоначально автоматическую очистку связанных записей отключить.
- `repost_publications`, `published_reposts`, `tiktok_tracked_publishes` переносятся в поля и историю соответствующих listings; `telegram_repost_queue` — в состояния входящих/объявлений. `tiktok_publish_attempts` и `tiktok_publish_throttle` — в settings.json. Старые таблицы удаляются после сверки внутри миграции; итоговая база содержит только две прикладные таблицы.

### settings.json в корне проекта

Один SettingsStore владеет файлом; UI настроек и workers не пишут его напрямую. Путь определяется явно от корня проекта (в текущем checkout `D:\git\rieltorSite\settings.json`), а не от случайного working directory. Для запуска JAR определить тот же абсолютный корень в конфигурации запуска.

Ключи файла:

- `schemaVersion`, `generation` — формат и версия записи;
- `telegram.stabilityWindowMinutes`, `telegram.topicTypeMapping`;
- `googleDrive.fileDelayMs`, `googleDrive.jobDelayMs`, `googleDrive.maxAttempts`, `googleDrive.retryBaseMs`, `googleDrive.maxCatalogPhotos`;
- `repost.minIntervalMs`, `repost.maxMessagesPer24Hours`, `repost.tiktokEnabled`, `repost.threadsEnabled`;
- `repost.runtime.blockedUntil`, `repost.runtime.lastReservedAt`, `repost.runtime.slotReservations` — сохраняемые резервы `{attemptId, listingId, reservedAt}` за окно квоты;
- `media.cleanupIntervalMs`, `media.orphanGraceMs`, `storage.migrationVersion`.

Все это JSON-значения, в том числе массивы/объекты. Настройки не должны разрастаться в копию объявлений: publishId, статусы и история каждого назначения остаются в listings. Секреты/OAuth остаются в существующем secrets.json; перенос токенов в settings.json не требуется.

Запись файла: блокировка единственного процесса-владельца, mutex для read-modify-write, валидация схемы, запись временного файла на том же диске, flush и атомарная замена с последней исправной резервной копией. Второй экземпляр приложения не запускает workers с тем же settings.json. Ручное редактирование — при остановленном приложении. Ошибка записи/повреждение не сбрасывает квоты: остановить новые репосты до восстановления; Drive и каталог могут продолжать при доступной конфигурации. settings.json и его временные/резервные файлы исключить из Git; пример конфигурации хранить отдельно.

Протокол резерва без общей транзакции:

1. После ожидания захватить в listings свежего кандидата и записать уникальный attemptId с состоянием PREPARED и lease.
2. Под блокировкой SettingsStore проверить актуальные лимиты и добавить резерв с тем же attemptId; атомарно записать файл. Если слот ещё недоступен, освободить кандидата и при следующем разрешении заново выбрать самое свежее объявление.
3. Только после успешной записи резерва отметить попытку SENDING в listings и делать внешний запрос. Сбой после резерва может консервативно занять лишний слот, но не разрешить сверхлимитную отправку.
4. После перезапуска PREPARED без резерва безопасно вернуть в очередь; PREPARED с резервом ещё не отправлялся и может быть продолжен с тем же attemptId. SENDING без надёжного ответа — UNKNOWN, затем сверка, без слепого повтора. Для реального внешнего статуса использовать состояния раздела 7.
5. Не удалять незавершённые резервы до сверки. По возрасту очищать только записи, которые уже не нужны для восстановления и вышли из окна квоты. Подсчёт pending shares получать из listings, включая legacy и все незавершённые попытки.

## 11. Критерии приёмки

- Перезапуск на 19-й минуте сохраняет время ожидания; до успешной проверки фото не скачиваются.
- Правка на 19-й минуте начинает новое 20-минутное окно; повтор того же события не продлевает его.
- Удаление, отсутствие доступа и timeout различаются; ошибка проверки не пропускает старый текст в каталог.
- Новая часть/правка альбома во время скачивания не создаёт дубль или объявление со смешанными версиями.
- Google Drive обрабатывает по одному заданию, берёт самое свежее доступное, работает при выключенных репостах и cooldown TikTok.
- Более 64 входящих не приводит к потере старых записей. Ошибочный Drive-пакет не блокирует следующий доступный.
- Сбой на каждом этапе записи manifest/файлов/транзакции восстанавливается без двойного объявления и битых фото.
- Новое объявление, поступившее во время ожидания мастер-лимитера, получает приоритет при освобождении слота.
- Успех TikTok и ошибка Threads дают true/false; FAILED не повторяется бесконечно. DRAFT и принятый publishId ещё не дают true.
- Перезапуск между внешним ответом и commit не вызывает слепой повтор; pending/UNKNOWN сверяются.
- Готовые объявления доступны на сайте независимо от статуса репостов; правки/удаления источника обновляют видимость.
- Ценовые границы, валюты, единицы цены, сочетания фильтров, пустые значения программ и пагинация проверены API-тестами на SQLite.
- Активные фото доступны после 4 дней; очистка истории не нарушает галерею и защиту от повторных публикаций.
- Миграция на копии версии 11 сохраняет историю, cooldown и pending, не выдумывает messageId.
- В целевой схеме ровно две прикладные таблицы; служебное состояние ключ–значение находится в корневом settings.json.
- Сбои до/после записи settings.json и до/после отправки не обнуляют квоту и не вызывают слепой повтор. Повреждённый файл и второй процесс не разрешают новые отправки.
- После frontend-интеграции: desktop/mobile, светлая/тёмная темы, фильтры, карточка объекта, навигация, формы, smoke и SEO-проверки.

На этапе подготовки этого плана проверены исходники и текущая версия схемы. Runtime, миграции и внешние сервисы не запускались; тестирование реализации относится к следующим этапам.
